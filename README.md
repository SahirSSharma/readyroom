# Readyroom

Preview the missing piece of an interview outfit, then hold that exact garment for pickup.

Readyroom is a web demonstration for students and small donated-clothing closets. It combines YouCam Clothes V4 outerwear previews with a complete hold, pickup, and return journey. The source garment remains available to inspect alongside its preview.

**This is a demonstration closet.** All six garments, condition notes, measurements, pickup dates, and pickup passes are illustrative. There is no university affiliation, physical stock, closet partnership, or established pilot. A preview is a visual suggestion; it does not establish physical fit, condition, or exact garment fidelity.

## Try the demonstration

Deployment target: [readyroom-youcam.vercel.app](https://readyroom-youcam.vercel.app). Deployment availability is not yet verified in this document.

1. Open the fitting room. A signed browser cookie creates your isolated demonstration closet; no account is required.
2. Choose a sample person or upload a photograph you have permission to use. Select one of the six sample blazers and inspect its illustrative measurements.
3. Give permission for photo processing and view a preview. Built-in samples can show a labeled, saved result previously generated by YouCam. Request a fresh live preview to exercise the provider integration; live provider errors are displayed rather than replaced with a simulated result.
4. Compare the source garment and preview, choose a demonstration pickup day, and hold the garment. A hold lasts **15 minutes**.
5. Open **Pickup desk** in the same session, collect the hold, and return it. Collection keeps the garment unavailable until it is returned. You can also release an uncollected hold.

Separate browser sessions have separate racks, so judges can explore without competing for demonstration stock. The pickup desk operates only the current session; it is not a production staff account. Refreshing a page preserves that session's state. Private-browsing sessions are useful for starting a separate demonstration.

## Run locally

Requires Node.js 20.9 or newer and npm. Install dependencies, copy the environment template, and add your credentials:

```sh
npm ci
cp .env.example .env.local
```

Set these server-only values in `.env.local`:

| Variable | Purpose |
| --- | --- |
| `YOUCAM_API_KEY` | Your YouCam API key, with Clothes V4 access and sufficient credits. |
| `SESSION_SECRET` | A cryptographically random secret of at least 32 characters. Keep it stable across deployments so sessions remain valid. |
| `BLOB_READ_WRITE_TOKEN` | Read/write token for a **private** Vercel Blob store. Production requires durable storage. |

You can generate a session secret locally:

```sh
node -e 'console.log(require("node:crypto").randomBytes(32).toString("hex"))'
```

Then start the app:

```sh
npm run dev
```

Open [http://127.0.0.1:3000](http://127.0.0.1:3000). Real previews require a valid YouCam key and consume provider credits. The inventory journey can run locally without Blob; development then stores JSON in `.local/workspaces/`. That fallback does **not** run in production.

The live-preview limits are constants in `lib/tryon.ts`: **8 attempts per browser session** and **200 attempts across the public deployment**. Counts are reserved before provider submission, so failed attempts can consume the allowance. Saved sample outputs do not consume live-preview allowance. These app limits are distinct from the provider's credit balance; the documented Clothes V4 rate is two credits per image. The code does not purchase credits or enable automatic recharge.

To deliberately use the local inventory store during development, set `STORE_FORCE_LOCAL=true`. `STORE_LOCAL_DIR` overrides its directory. Neither setting bypasses the production storage requirement. The local store supports one application process; use private Blob for multiple instances.

## Verify

```sh
npm test
npm run typecheck
npm run build
```

The inventory tests cover concurrent holds, exact hold expiry, isolated workspaces, duplicate pickup rejection, returns, invalid input, signed-cookie tampering, same-origin writes, concurrent render accounting, and production storage failure. Live Blob integration was also exercised on September 27, 2026: six simultaneous holds produced one winner, and five concurrent counter increments were preserved. Build and deployed browser checks are separate release requirements; a passing unit suite is not evidence that the deployed provider integration works.

## Architecture

- Next.js App Router and React, with TypeScript.
- `lib/catalog.ts`: six immutable demonstration garment definitions.
- `lib/session.ts`: expiring HMAC-signed, HttpOnly workspace cookie; secure in production.
- `lib/store.ts`: one private Blob per workspace; fresh reads and ETag-conditional writes, with bounded conflict retries. Development-only JSON storage uses a process lock and atomic replacement.
- `lib/closet.ts`: hold expiry and reservation state transitions.
- `lib/tryon.ts` and `lib/youcam.ts`: input validation, saved/live preview handling, atomic attempt allowances, and the YouCam Clothes V4 integration.
- Server routes: provider credentials and persistent state stay outside browser code.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/closet` | Start/read the current demonstration closet. |
| `POST /api/reservations` | Hold an available item with `{itemId,pickupDay}`; dates use `YYYY-MM-DD`. |
| `PATCH /api/reservations/[id]` | Apply `{action: "release" | "collect" | "return"}`. |
| `POST /api/tryon` | Start a preview using an image or sample, a garment ID, and processing consent. |
| `GET /api/tryon/[taskId]` | Read the current session's preview status. |

Reservation writes require both the signed session and a matching `Origin` header. An item has at most one active hold or collection within its workspace. Rendering does not reserve stock; the hold operation checks availability again.

## Data and responsible use

Readyroom does not ask for names, email addresses, or payment details. A photo submitted for preview is sent to Perfect Corp's YouCam service. Its processing and retention are governed by the provider's terms; this project does not claim to control provider retention. Use only photographs you have permission to process. The built-in fictional sample people allow a judge to test without uploading a personal image.

Readyroom does not persist uploaded source-image bytes. Its workspace state contains task metadata and a provider result location. Live output is served through a session-owned route; provider result links can expire. The checked-in saved examples use only fictional sample people and garments and are public demonstration assets.

Private storage and session ownership protect demonstration state. This is not a production clothing-closet deployment: a real pilot would require authorized inventory, staff access controls, an agreed photo-retention policy, accessibility and usability testing, and physical pickup operations.
